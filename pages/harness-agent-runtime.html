核心结论

Harness 可以理解为包围模型调用与工具循环的一层 Agent Runtime。它组织任务上下文、工具面、会话状态、文件与 shell 环境、权限与审批、记忆与压缩、子代理、观测和验证。

ReAct 描述了 Agent 如何在“推理—行动—观察”之间循环；Harness 决定这个循环运行在哪个环境里、携带哪些状态、拥有怎样的能力边界，以及什么条件构成一次完成。

不同 harness 的差异，集中体现在几个问题上：哪些能力写进内置 runtime，哪些能力通过 middleware 或 plugin 接入；哪些信息进入 system prompt，哪些信息保存在 session；哪些规则由模型理解，哪些规则由权限、沙箱和验证机制执行。

一、从 ReAct 循环开始

ReAct 论文把语言模型的工作描述成一种交替过程：模型生成推理，选择行动，接收环境观察，再继续推理。对 Agent 来说，行动通常表现为工具调用，观察通常表现为工具结果或环境状态。

这个循环本身很小，工程复杂度集中在循环周围。一次真实的 Agent turn 需要回答：模型看到哪些文件和历史？工具由谁执行？工具调用是否需要审批？失败后如何继续？会话能否恢复？任务完成如何确认？

因此，ReAct 是理解 harness 的入口。沿着它向外展开，就能看到 context、tool、state、policy、extension 和 verification 六个运行时方向。

循环内部

模型读取上下文，产生 reasoning 和 tool call；runtime 执行工具，将结果重新送入下一步。

循环周围

runtime 组装上下文，维护 session，决定工具权限，管理执行环境，并留下可复盘的事件与验证结果。

参考：ReAct: Synergizing Reasoning and Acting in Language Models；AI Harness Engineering: A Runtime Substrate for Foundation-Model Software Agents。

二、Harness 的运行时地图

将不同 harness 放在一起观察，可以得到一张相对稳定的运行时地图。具体产品的命名不同，承担的职责高度相似。

运行时层 核心问题 常见实现
Context / Prompt 本轮模型看到什么？哪些项目规则、技能和工具指导进入 prompt？ system prompt、项目 instruction、skills、middleware sections
Loop / Turn 一次请求如何推进？工具结果如何触发下一步？什么时候结束？ ReAct loop、turn/step、Plan/Act、task driver
Action / Tool Agent 能够读什么、写什么、执行什么、查询什么？ filesystem、shell、search、web、LSP、MCP、subagent

这张地图也是本文的比较方法。每个 harness 小结都围绕核心工具、prompt 组装、状态机制、独有特性和设计哲学展开。这样可以看到实现细节背后的取舍。

三、Deep Agents：Middleware 组装运行时

Deep Agents 官方将自己定位为 “batteries-included agent harness”。它建立在 LangGraph runtime 和 LangChain agent loop 之上，通过 middleware 组合出一套带有明确偏好的 Agent Runtime。

从 create_deep_agent 到 Agent Runtime

Deep Agents 的入口函数承担的是运行时装配工作。它会解析 model、profile、backend 和 subagent 配置，组合内置与自定义 middleware，生成 system prompt，再把组装结果交给 LangChain agent loop。实际运行中的 state、checkpoint、streaming 和 interrupt 由 LangGraph 负责。

create_deep_agentmodel · profile · backend -> Middleware stacktools · prompt · state -> LangChain Agent Loopmodel · tool calls -> LangGraph Runtimecheckpoint · interrupt · resume

因此，middleware 位于 Agent Loop 内部。它可以参与模型调用前的上下文准备、工具调用前后的处理、状态更新以及上下文压缩。Deep Agents 的能力模块也由此获得了统一的接入位置。

核心能力模块：工具、Prompt、State 与 Backend

Filesystemls、read_file、write_file、edit_file、glob、grep描述虚拟文件系统和文件操作方式backend 决定文件如何读写；合适的 backend 可以暴露 execute

这张表说明了一件重要的事情：Deep Agents 的内置能力通常同时包含工具、prompt、state 和执行机制。工具只是能力模块暴露给模型的表面接口，middleware 才是把这些部分连在一起的装配单元。

一次工具调用如何经过 Middleware

准备 state -> 组装 prompt确定可见工具 -> 模型选择工具 -> middleware / policy检查、拦截、修改 -> backend 执行 -> 更新 state压缩或进入下一轮

模型负责从当前工具集合中选择动作，middleware 负责准备模型看到的能力面和上下文，backend 负责执行实际操作，LangGraph 负责保存和恢复运行状态。每一层都有清晰的控制点，工具调用也因此拥有了可观测、可审批和可恢复的路径。

System prompt、State 与 Middleware

Prompt 组装

assembled system prompt 可以包含 base agent prompt、todo 指导、memory、skills、virtual filesystem、subagent、custom middleware 和 HITL 指导。能力模块通过 prompt 把“什么时候使用工具、工具如何协作”交给模型。

State 组装

middleware 可以贡献结构化 state 字段。消息、todos、工具结果、interrupt 和摘要都能沿着 LangGraph 的运行状态延续，并由 checkpointer 支持恢复。

大工具结果写入文件系统、主上下文保留引用，是 Deep Agents 处理长任务的典型方式。Context engineering 在这里拥有明确的 runtime 位置：它参与每轮请求的 prompt、工具集合和历史状态准备。

设计哲学：把 Agent 能力做成可组合部件

Deep Agents 的默认能力拥有一致的形状：工具负责让模型采取行动，prompt 负责解释使用方式，state 负责延续过程，backend 或 policy 负责确定执行边界。用户可以替换 backend、添加 middleware、配置 subagent，同时保留 LangGraph 作为底层运行时。

Deep Agents 把“计划、文件、记忆、技能、子代理和人工审批”组织成一组可组合 middleware，让一个稳定的模型—工具循环获得更长的工作半径。

参考：Deep Agents README、Customization、Context engineering、Architecture。

四、Pi：小内核与深扩展面

Pi 采取另一种组织方式：默认 runtime 保持小而清晰，复杂能力通过 TypeScript extensions、skills、prompts、packages 和 themes 接入。Pi 的 extension 以宿主插件模块的形式存在，可以向宿主注册事件、工具、命令、快捷键和 UI 能力。

最小内核与动态 Prompt

默认工具

核心工具围绕文件读取、编辑、写入和 shell 执行展开；具体工具集合由当前配置和启用状态决定，扩展还可以注册额外工具。

宿主 API

Extension API 提供事件监听、工具注册、命令注册、快捷键、UI、session 操作和 Provider 请求拦截等入口。

Pi 的 system prompt 会根据当前启用的工具、工具说明片段、prompt guidelines、工作目录、项目 context files 和 skills 动态构造。工具集合本身成为 prompt 的一部分，扩展可以通过注册工具和生命周期事件改变 Agent 的能力面。

Extension API 的技术形态

一个 extension 通常导出默认函数。宿主加载模块后传入 ExtensionAPI，扩展通过这个对象向 Pi 注册能力：

export default function (pi: ExtensionAPI) {
  pi.on("tool_call", async (event, ctx) => {
    if (event.toolName === "bash") {
      const ok = await ctx.ui.confirm("运行 bash？", "");
      if (!ok) return { block: true, reason: "用户拒绝执行" };
    }
  });

  pi.registerCommand("hello", {
    description: "Say hello",
    handler: async (_args, ctx) => {
      await ctx.ui.notify("hello");
    },
  });
}

这段代码同时展示了 Pi extension 的两个方向：它可以参与 Agent 行为，也可以参与宿主交互。前者通过生命周期事件实现，后者通过 command、UI 和快捷键等宿主 API 实现。

事件执行时机可影响的对象

Pi 的扩展面横跨三个边界：Agent 行为、Provider 请求和宿主产品能力。尤其是 before_provider_request，它允许扩展在模型请求即将发出时直接观察或替换 payload；tool_call 则位于工具执行前，可以实现权限确认、路径保护和确定性拦截。

Prompt、Session 与 Extension State

Prompt 构造

selectedTools、toolSnippets、promptGuidelines、工作目录、项目 context files 和 skills 共同影响 system prompt。before_agent_start 与 context 还可以继续调整本轮上下文。

状态持久化

扩展短期状态可以保存在进程内；需要跨会话或分支恢复的状态，应写入 session entry 或工具结果的 details，并在会话启动时根据 branch 重建。

Pi 将 session 作为扩展可以参与的事实来源。扩展可以追加事件，也可以根据当前分支重新计算自己的状态。这种方式给了插件作者很大的自由度，同时要求每个扩展自行设计状态一致性和恢复策略。

设计哲学：把宿主做成可编程平台

Pi 的核心运行时保持小而清晰，变化通过 Extension API 向外展开。扩展可以按照任务需要重新组合工具、prompt、权限、命令、界面和会话逻辑，Agent 的能力边界也随之成为一个可编程对象。

Pi 把 Agent 的生命周期、工具系统、Provider 请求和交互界面暴露给扩展，让 coding agent 从一个固定产品变成一组可以重新编排的宿主能力。

两种机制都提供了 ReAct 循环之外的控制面，控制面的边界各有侧重：Deep Agents 重点管理 Agent 如何运行，Pi 进一步开放 Agent 产品如何被改造。这个差异也为后文理解 DeepSeek Harness 的插件化设计提供了参照。

五、OpenCode：显式工具面与权限语法

OpenCode 把 provider、agent、工具、权限、skills、MCP 和插件放在一套可配置的 runtime 里。它的特点集中在“每个控制面都拥有显式配置”：模型可以更换，agent 可以切换，工具可以细分，权限可以落到命令和路径，扩展可以通过插件进入生命周期。

从 Session Prompt 到工具结算

从源码路径看，OpenCode 的 session/prompt 是一次 Agent turn 的重要汇合点：它读取 session，组装当前 agent、system prompt、instructions、skills、工具 registry 和 MCP 工具，向 provider 发起请求；工具执行前后再经过插件 hook，结果写回 session，必要时进入 compaction。

Session promptagent · system · instructions -> Tool registrybuilt-in · custom · MCP -> Permissiontool · command · path -> Execute + hooksbefore · execute · after -> Session / compactionpersist · summarize · retry

这条路径说明 OpenCode 的 Agent Loop 由多个可替换服务共同完成。工具注册决定模型能看到什么，permission 决定动作是否可以继续，tool settlement 负责真正执行，session 负责让结果进入下一轮和后续恢复。

核心工具面：从代码操作延伸到上下文操作

能力区代表工具运行时职责
文件与命令read、edit、write、apply_patch、bash读取、修改和执行项目中的实际工作
代码理解grep、glob、lsp建立搜索、文件发现和语言服务能力
任务与指导todowrite、todoread、skill维护显式任务状态，并按需加载工作方法
外部信息webfetch、websearch、MCP tools把网络和外部服务接入同一工具权限体系
交互question把需要用户决策的分支纳入 Agent Loop

OpenCode 文档把内置工具、custom tools 和 MCP servers 放在同一张工具地图上。这样做的效果是：模型看到的能力来自统一 registry，权限规则也可以用同一套模式匹配处理内置工具、自定义工具和 MCP 工具。

Permission：把治理细化到工具输入

三种决策

allow 直接执行，ask 请求用户批准，deny 阻止动作。默认工具可以运行，项目配置再针对敏感能力增加约束。

细粒度匹配

规则可以匹配工具名、bash 命令、文件路径和外部目录。最后匹配的规则生效，agent 还可以覆盖全局 permission。

例如，bash 可以把所有命令设为 ask，再把 git status 设为 allow，把 git push 设为 deny；edit 也可以只开放某个目录。--auto 只改变原本需要询问的动作，显式的 deny 仍然生效。

这种 permission 设计把“模型能不能调用工具”和“这次具体输入能不能执行”放进同一个 policy 层。权限规则因而拥有了比 system prompt 更稳定的约束力。

Agent、Skill 与 Plugin：三个不同的扩展粒度

OpenCode 的 agent 配置可以指定 model、prompt、permission 和 tools，并通过 mode 区分 primary、subagent 和 all。Task 工具负责调用子 Agent，permission.task 可以进一步限制某个 Agent 可以调用哪些子 Agent。

Skills 采用 progressive disclosure：模型先在 skill 工具描述中看到可用 skill 的名称与简介，选择之后再加载具体内容；skill 自身也受 pattern-based permission 控制，deny 的 skill 会从可见列表中消失。

Plugin 则位于 runtime hook 层。它是一个 JavaScript/TypeScript 模块，可以从 npm 或全局/项目插件目录加载，插件函数接收项目、worktree、目录、SDK client 和 shell API，并返回 hooks 或 custom tools：

export const BashGuard = async () => ({
  "tool.execute.before": async (input, output) => {
    if (input.tool === "bash") {
      // 可以检查或修改即将执行的参数
      output.args.command = output.args.command.trim();
    }
  },
});

插件按全局配置、项目配置、全局目录、项目目录的顺序加载，hook 按加载顺序执行。除了工具执行 hook，插件还可以参与文件、消息、命令、session compaction 和日志等事件。

Session 与 Compaction：保留事实，重建上下文

OpenCode 的 session 持久化完整对话和工具结果，compaction 为模型上下文生成结构化 checkpoint，并保留近期上下文尾部。每次 provider 调用前，runtime 会估算 system prompt、messages 和工具说明的整体大小；超过模型上下文预算后，先完成 compaction，再用新的 checkpoint 重建请求。

这套机制把“历史事实”和“当前模型视图”分开：session 负责保留可恢复的记录，compaction 负责生成有限长度的工作上下文，plugin 还可以通过 experimental.session.compacting 注入必须跨压缩保留的信息或替换压缩 prompt。

OpenCode 的设计重点是把 Agent Runtime 写成一套显式控制面：工具、agent、permission、skill、plugin 和 session 各自拥有可读配置，同时通过统一的 prompt 和 tool dispatch 路径协作。

它体现的设计哲学是“provider-neutral + 显式治理 + 可组合服务”。用户可以阅读和修改大部分 runtime 行为，模型选择、工具可见性、执行权限、子 Agent 和上下文压缩也因此成为同一套配置语言中的不同对象。

参考：Tools、Permissions、Agents、Skills、Plugins、Compaction、Session prompt source。

六、Cline：Plan/Act、Stateful Core 与插件 Hook

Cline 的技术形态适合从 SDK 架构展开。它把无状态的 Agent Loop 放在 @cline/agents，把模型适配放在 @cline/llms，把 session、持久化、配置发现、RPC 和运行时宿主放在 @cline/core，再由 CLI、VS Code、JetBrains、Kanban 或自定义应用提供具体 host。

从 Host 到 Agent Loop

HostCLI · IDE · SDK app -> RuntimeHostlocal · hub · remote -> ClineCoresession · config · persistence -> Agentloop · tools · streaming -> LLM handlersprovider request / response

官方 SDK 架构把这条链路拆得很清楚：host 构造 RuntimeHost，core 准备运行时并创建 Agent，@cline/agents 驱动循环，@cline/llms 处理模型，core 最后保存 state、artifacts 和 metadata。Hub runtime 还可以让多个客户端连接同一个 session，继续接收结构化事件流。

Cline 的工具面同时覆盖环境操作和交互控制。用户可以把它当作代码编辑器里的执行 Agent，也可以把 MCP、浏览器、提问和新任务视为工作流的一部分。SDK 层还提供归一化的 bash、editor、read_files、apply_patch、search 和 fetch_web 等工具接口。

Plan/Act：把模型决策放进可审阅的状态机

Plan mode

可以读取代码、搜索和讨论方案，运行时禁止修改文件和执行命令。它把探索、架构决策、边界讨论和计划形成集中在一个低副作用阶段。

Act mode

沿用 Plan 阶段的完整上下文，获得文件修改和命令执行能力。不同模式可以选择不同模型，用户也可以在复杂任务中多次往返。

Plan/Act 的价值体现在权限和上下文的同时切换：Plan 阶段降低工具权限，Act 阶段恢复执行能力；两阶段共享对话历史，计划因此成为后续执行的正式输入。Cline 还提供 checkpoints，让文件变更可以回滚和比较。

Plugin 与 Hook：能力注册和生命周期拦截

Cline plugin 是 TypeScript 模块，可以是单文件，也可以是带依赖和资源的 package。加载过程包含 resolve、validate、setup、activate 四个阶段：先收集插件，再校验 manifest 与 capabilities，随后注册工具、命令、rules、providers 和 hooks；session 启动后，注册表被冻结。

const plugin: AgentPlugin = {
  name: "guard",
  manifest: { capabilities: ["hooks"] },
  hooks: {
    beforeTool({ toolCall }) {
      if (toolCall.toolName === "run_commands") {
        return { stop: true, reason: "需要人工确认" };
      }
    },
    afterRun({ result }) {
      if (result.status === "completed") {
        // 记录成功完成事件
      }
    },
  },
};
Hook位置典型用途
beforeRun / afterRun一次 user turn 前后初始化、指标、完成通知
beforeModel / afterModel模型请求前后注入上下文、修改 request、检查模型输出
beforeTool / afterTool工具执行前后审计、脱敏、阻止危险调用、替换结果
onEventruntime event 流驱动 UI、遥测和外部事件管道

Cline 同时保留 file hooks 和 typed runtime hooks：前者适合工作区脚本，后者适合可复用插件。插件还可以通过 message builder 做上下文重写，通过 rule 注入 prompt 规则，通过 provider 和 automation event 扩展宿主能力。

Session、Compaction 与完成判定

Cline Core 负责 session persistence、SQLite 存储、配置发现和多进程运行。完整 transcript 作为 canonical history 保留，compaction state 作为单独 artifact 保存；恢复时先校验 compaction 覆盖的历史前缀，再把边界之后的新消息投影回工作上下文。

文件变更还可以通过 Git-based checkpoint 追踪和回滚。一次 Agent turn 的完成也拥有确定性信号：当前 SDK 观察成功的 submit_and_exit tool call，并据此发出 task.completed；旧 Cline 产品中的 attempt_completion 是对应的交互语义。

Cline 把 coding agent 拆成无状态 Agent Loop、状态化 Core 和可替换 Host，再用 Plan/Act、checkpoint、plugin hook 和 session persistence 把人机协作编排成完整工作流。

它体现的设计哲学是“分层运行时 + 显式协作状态”。Agent 负责模型与工具循环，Core 负责事实状态和恢复，Host 负责交互与部署形态，Plugin 和 Hook 负责可复用扩展。

参考：All Cline Tools、Cline SDK、SDK Architecture、Plugin guide、Plan & Act、Cline overview。

七、Claude Code、Codex 与 Grok Build

这三个 coding harness 都把文件、命令、项目上下文和权限边界做成了相对完整的产品能力，但各自强调的控制面不同。

Claude Code：模型驱动扩展与确定性护栏

工具面：Read、Write、Edit、Bash、Glob、Grep、web search、MCP，以及 subagent 和交互工具。

上下文：CLAUDE.md 作为持久项目上下文，skills 按需加载，auto memory 提供机器级记忆，MCP 连接外部服务。

独有特性：hooks 负责生命周期自动化，权限系统可以在工具执行前进行 allow、ask、deny 决策。

设计取向：模型负责组合能力，hooks 和 permissions 负责确定性规则。

工作方式 · 扩展面 · 权限

Codex：沙箱、审批与仓库级上下文

工具面：shell/patch/file changes、web search、MCP、skills 和 hooks。

上下文：通过层级化的 AGENTS.md 注入仓库、目录和全局工作约束，越靠近当前目录的 instruction 拥有更高局部性。

独有特性：sandbox 负责技术边界，approval policy 负责确认时机，两者形成分层治理。

设计取向：把“在哪里能写、能否联网、何时需要询问”落实为 runtime policy。

Codex CLI · AGENTS.md · Sandboxing

Grok Build：开源 Runtime 与协议互操作

工具面：读取、编辑、搜索代码，shell、web、长任务，以及计划和并行 subagents。

扩展面：官方介绍公开了 agent loop、context assembly、tool dispatch、skills、plugins、hooks、MCP、subagents 和 ACP。

独有特性：Plan mode 支持用户审阅、修改和批准计划，runtime 以 Rust 实现并支持 local-first 配置。

设计取向：公开 runtime 结构，连接计划审阅、扩展系统和 Agent 间协议。

xAI 开源介绍 · Grok Build repository · CLI 发布介绍

这三者共同说明：coding harness 的产品差异逐渐集中在上下文装配、权限策略、生命周期 hook、会话恢复和验证工作流。单看模型调用接口，很难解释用户体验与安全边界的差异。

八、DeepSeek Harness：Everything is a Plugin

DeepSeek Harness（CLI 名称为 dsh）是官方开源的 Agent Harness，目前处于 developer preview。官方架构建立在 Cordis 之上，核心口号是 “Everything is a Plugin”。

插件树：运行时能力的组合方式

DSH 把模型适配器、工具注册表、session log、system prompt、agent loop、filesystem、shell、skills、subagents、jobs、workflow、sandbox、approval、persistence、telemetry、web/ACP/SDK 都放进 Cordis plugin tree。插件通过 service definition、provider、consumer 形成能力 seam，配置层可以在启动时替换、插入或卸载具体实现。

官方架构文档列出的 core packages 也呈现了这种边界：

Package 运行时职责 对 Agent 行为的影响
core/session 维护 append-only SessionEvent log 决定历史、恢复、fork、replay 和持久化的事实来源
core/system-prompt 组装 prompt sections 与 tool schemas 决定每个 step 的模型可见上下文
core/tools 维护 scoped tool registry 与 guarded execution 决定工具发现、权限和执行阶段
core/agent-loop 提供默认 driver 推进 turn、step、模型请求和工具工作
llm/llm 提供消息、流和模型适配 seam 支持模型 provider 的替换

Turn / Step：两层 Agent Loop

DSH 将一次工作拆成两个层次：

  • Step：一次模型请求，以及这次请求触发的工具执行。
  • Turn：从输入被接收开始，到没有待处理输入或工具工作时结束的任务区间。

典型路径可以写成：

input inbox → claim next-step input → agent/pre-step → step/start → 从 session log 派生 model history → 组装 system prompt 与 tool schema → agent/request → llm/stream → assistant chunks / message → tool/call → policy / approval / sandbox / execute → tool/result → step/end → 下一 step 或 turn/end

Session Event Log：模型可见内容的事实来源

DSH 的 session 采用 append-only typed event model。LLM history 从 log 派生，assistant chunks、tool call/result、request header 等事件共同构成可回放状态。官方架构特别强调：模型可见的输入需要能够从 log 重建，渲染后的 system prompt 和工具 schema 也记录在 request header 中。

这一设计让 fork、resume、replay、UI trajectory、telemetry 和 persistence 使用同一份状态来源。状态的可追溯性因此成为 runtime contract。

System Prompt：可排序、可 Shadow、可 Complete

system-prompt 是独立 package。插件可以按名称和顺序注册 PromptSection、动态 prompt context、工具 schema provider 和变量；scoped section 可以 shadow 全局 section。standard preset 会组装 persona、agent instructions、bash、filesystem、skills、goal、plan、compaction、delegation/workflow 等能力。

minimal preset 使用 complete: true 的固定 persona，只保留有限工具，体现了 DSH 的两种 prompt 形态：一套可由插件逐段组合的 prompt，以及一套由 preset 完整接管的 prompt。

工具、记忆与安全边界

  • 工具：ToolDefinition 同时描述参数 schema、输出、执行函数、调度元数据和展示信息；registry 支持 scope、shadowing、allow/deny 和 deny-only guard。
  • 执行：工具经过 pre-execute、policy/guard、approval、sandbox、execute、post-execute 等阶段，并把调用与结果写入事件流。
  • 记忆：session persistence 属于核心状态；长期语义记忆通过 default-off 的 MCP memory overlay 接入，部署者可以选择后端和数据治理边界。
  • 安全：approval、sandbox、工具 policy、审计事件和 runtime invariants 形成多层约束。
DSH 的设计哲学可以概括为：插件化能力、事件溯源状态、可撤销生命周期、分层安全边界与真实运行路径验证。

与 Deep Agents 对照来看，Deep Agents 以 middleware 组装一套 opinionated harness；DSH 把 service、lifecycle 和事实来源也纳入统一的插件组合。前者适合表达“如何把 Agent 能力装配起来”，后者适合观察“一个 Agent Runtime 如何把自身拆成可替换部件”。

参考：DeepSeek Harness 官方页面、官方仓库、架构文档、Agent lifecycle、Session subsystem、System prompt subsystem、Cordis。

九、Langfuse 与 Vercel：跨越 Runtime 的两层视角

Langfuse：观测、评估与 Prompt 反馈

Langfuse 的核心工具面集中在 trace、observation、prompt、dataset、evaluation 和 agent-facing access。它通过 Agent Skill、CLI 和 MCP，让 coding agent 查询 traces、管理 prompts、创建 evaluations，并把运行反馈带回开发流程。

从 harness 视角看，Langfuse承担的是 observability/evaluation plane：它记录 Agent 做了什么、工具如何执行、哪里产生失败、哪个 prompt/tool/version 影响了结果，并支持后续评估和迭代。

参考：Langfuse Agents、Observation types、Agentic access。

Vercel AI SDK：统一接入层如何保留差异

Vercel AI SDK 的 Harness 抽象提供了一个观察不同 runtime 的统一入口：HarnessAgent、adapter、sandbox provider 和 session。当前 adapter 列表包括 Claude Code、Cline、Codex、Deep Agents、Grok Build、OpenCode 和 Pi。

官方文档将工具面分成三类：

工具面 执行者 设计含义
Runtime built-in tools 底层 harness 工具与原生权限、session、sandbox 和事件流绑定
Host-executed AI SDK tools 宿主应用 应用可以把自有业务能力注入 Agent，同时保留宿主执行边界
External MCP tools MCP server 工具通过协议连接外部服务，拥有独立生命周期与权限边界

统一 API 保留了 runtime 差异：Claude Code 的 adapter 暴露 read/write/edit/bash/glob/grep/webSearch；Pi 暴露 read/write/edit/bash/grep/glob/ls；OpenCode 还包括 webfetch、skill、todowrite、agent；Codex 的文件变化则以动态事件体现。这个差异本身就是 harness 设计的一部分。

参考：HarnessAgent、Tools、Skills、Harness adapters。

十、把 Harness 读成一组设计选择

不同项目采用了不同的组合方式，但可以从内置能力反推出它们的设计取向。

观察到的能力 体现的设计选择
write_todos、todowrite、Plan mode 任务分解和任务状态拥有显式载体，模型的短期记忆获得外部支撑
文件系统、context offload、compaction 上下文被当作有限资源，结果可以外部化、压缩和按需取回
task、subagent、ACP 上下文隔离、并行执行与 Agent 间委派成为 runtime 能力
SKILL.md、skill()、plugin 能力通过发现、按需加载和生命周期管理进入运行时
middleware、hook、permission、sandbox 扩展逻辑与确定性治理分别拥有自己的接入点
session log、event store、replay 状态拥有可恢复、可审计、可回放的事实来源
trace、evaluation、verification “完成”拥有可观察和可检查的判定依据

如果把这些能力再抽象一层，Harness 的核心设计问题可以收敛成三问：

  1. 哪些能力应该成为可替换组件？
  2. 哪些状态应该成为持久、可回放的事实来源？
  3. 哪些边界应该由 runtime 强制执行，哪些边界交给模型理解？

Deep Agents、Pi、OpenCode、Cline、Claude Code、Codex、Grok Build 和 DeepSeek Harness 的差异，正是它们对这三问给出的不同答案。Harness 的价值也由此显现：它让 Agent 的能力、状态和约束获得了可设计、可替换、可验证的工程边界。
